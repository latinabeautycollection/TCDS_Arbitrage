# 10C Compatibility with Reviewed 10A and Reviewed 10B

The attached reviewed 10B establishes the production-safe shared runtime:

`src/domains/operations/infrastructure/operationsRuntime.ts`

10C imports that existing runtime rather than creating another database pool/logger/metrics/tracer.

## Reused 10A objects

10C uses but does not recreate:

- `operations.notification_deliveries`
- `operations.delivery_attempts`
- `operations.notification_outbox`
- `operations.provider_receipts`
- `operations.dead_letters`
- `operations.sms_subscriptions`
- `operations.channel_controls`
- `operations.channel_rate_limits`
- `operations.rate_limit_buckets`
- `operations.claim_notification_outbox(...)`
- `operations.sms_delivery_currently_eligible(...)`
- `operations.suppress_ineligible_sms()`
- `operations.record_provider_acceptance(...)`
- `operations.record_final_delivery(...)`

## Reused 10B objects

10C uses the provider-ready rows generated by 10B and requires:

- `operations.notification_decisions`
- reviewed 10B runtime composition
- reviewed 10B migrations 513/514/515

It does not update or reinterpret policy candidates, selected recipients, suppression planning, or template rendering.

## New 10C database namespace

10C adds only:

- `operations.delivery_reconciliation_tasks_10c`
- functions whose names end in `_10c`
- two additive receipt metadata columns required for ordered Telnyx delivery evidence

This naming policy is intentional collision protection.

## Provider ownership

The existing enterprise Microsoft Graph and Telnyx implementations are connected through ports/adapters.

10C does not create:
- `microsoftGraphEmailProvider.ts`
- `telnyxSmsProvider.ts`
- `emailDeliveryWorker.ts`

This avoids overwriting the provider work already completed.
